# Words Game — спецификация MVP и архитектурный дизайн

- **Дата:** 2026-11-22
- **Статус:** согласовано
- **Первая игра:** `WORD_CHAIN`
- **Назначение документа:** источник истины по продуктовым правилам, состояниям, UX и критериям приёмки

Детали реализации не дублируются здесь: архитектура описана в `docs/architecture.md`, данные — в `docs/data-model.md`, контракты — в `docs/api.md`, запуск и проверка — в `docs/development.md`.

## 1. Цель

Создать мобильный сайт для компании, которая играет вживую. Участники через телефоны создают комнату или входят по коду, загадывают друг другу слова, используют подсказки во время объяснения и отмечают угадывание. Система обеспечивает честное распределение, скрытие собственного слова и однозначный итоговый рейтинг.

MVP должен быть работающей вертикальной частью продукта, а не только демонстрацией интерфейса. Общий каркас комнат должен позволять добавлять другие игры без переработки входа, участников и синхронизации.

## 2. Термины

- **Игра / комната (`Game`)** — одна сессия от создания до финала.
- **Игрок (`Player`)** — участник конкретной комнаты. Один человек в разных комнатах представлен разными записями.
- **Админ** — игрок с правами управления комнатой. Админ участвует в игре наравне с остальными.
- **Автор слова** — игрок, который вводит слово.
- **Адресат** — игрок, которому это слово загадано.
- **Собственное слово игрока** — слово, адресатом которого является этот игрок.
- **Ревизия** — монотонно увеличивающийся номер состояния комнаты.
- **Гостевая сессия** — зашифрованная cookie, связывающая браузер с `playerId`.

## 3. Роли и разрешения

| Действие | Игрок | Админ |
| --- | --- | --- |
| Подключиться до старта | Да | Да |
| Изменить собственную готовность | Да | Да |
| Изменить настройки | Нет | Да |
| Удалить участника в лобби | Нет | Да, кроме себя |
| Начать игру | Нет | Да |
| Ввести собственное слово | Да | Да |
| Отметить собственное угадывание | Да | Да |
| Досрочно завершить | Нет | Да |
| Отменить этап ввода слов | Нет | Да |

Все разрешения проверяются сервером для каждого запроса. Скрытие кнопки не является авторизацией.

## 4. Область MVP

### Входит

- создание и подключение по коду;
- один админ, который также является игроком;
- 3–12 участников;
- готовность, настройки лобби и запуск;
- один замкнутый круг назначений;
- ввод и редактирование слова до общего старта угадывания;
- опциональное скрытие адресата на этапе ввода;
- персональная подсказка в живой игре;
- угадывание, места, очки и финальная таблица;
- автоматическое и досрочное завершение;
- восстановление после перезагрузки и переподключение SSE;
- возврат из этапа ввода слов в лобби при зависшей попытке.

### Не входит

- регистрация, пароли, OAuth и вход на другом устройстве;
- постоянный рейтинг между комнатами;
- несколько раундов внутри одной комнаты;
- подключение новых игроков после старта;
- удаление или самостоятельный выход участника после старта; угадавший становится зрителем, но остаётся в комнате;
- чат, голосовая связь и автоматическое объяснение слов;
- модерация слов;
- другие игровые типы;
- горизонтальное масштабирование realtime-сервера.

## 5. Жизненный цикл

Публичная модель использует четыре состояния:

```text
LOBBY -> ASSIGNING_WORDS -> PLAYING -> FINISHED
   ^             |
   |--- отмена ---|
```

Недопустимые переходы возвращают конфликт состояния и не изменяют данные.

### 5.1 Создание и вход

1. На главной пользователь вводит имя и создаёт комнату либо вводит имя и код существующей комнаты.
2. Создатель становится админом и первым игроком. Его готовность изначально выключена.
3. Код состоит из шести символов алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` и уникален.
4. Приглашение может быть ссылкой с кодом, но ввод имени остаётся обязательным для нового устройства.
5. Подключение разрешено только в `LOBBY`, если участников меньше 12.
6. После успешного создания или входа сервер устанавливает гостевую cookie.
7. Повторный вход с cookie игрока, который уже принадлежит этой комнате, возвращает текущее состояние и не создаёт дубликат.

### 5.2 Лобби

- Отображаются код, ссылка-приглашение, имена, роль админа и готовность.
- Каждый игрок управляет только собственной готовностью.
- Админ может запустить игру только при 3–12 участниках и готовности всех, включая себя.
- Настройки может менять только админ и только в `LOBBY`.
- Изменение настройки скрытия имён не сбрасывает готовность.
- Админ может удалить другого игрока в лобби. Игрок может выйти сам.
- При выходе админа роль переходит к самому раннему оставшемуся участнику по `joinedAt`, затем по `id` как детерминированному критерию.
- Разрыв соединения не является выходом и не передаёт роль админа.
- Если последний участник выходит, пустая комната удаляется.

### 5.3 Настройка скрытия адресата

Поле: `hideTargetNamesDuringSetup`, по умолчанию `false`.

- `false`: на этапе ввода автор видит «Загадай слово Маше».
- `true`: автор видит только «Введи загаданное слово».
- При `true` в `ASSIGNING_WORDS` собственный `setup.target = null` и `setup.targetHidden = true`: связь автор → адресат (идентификатор и имя адресата) не передаётся автору ни в персональном DTO, ни в SSE, ни в RSC-ответе.
- Общий список участников `players` остаётся видимым без изменений: настройка скрывает только собственное назначение адресата, а не ростер комнаты.
- После перехода к `PLAYING` назначения и имена видны по общим правилам подсказки независимо от настройки.
- Настройка не скрывает автора слова и не влияет на итоговое раскрытие.

### 5.4 Построение назначений

При запуске сервер в одной транзакции:

1. Повторно проверяет состояние, число игроков и готовность.
2. Получает всех участников и перемешивает их unbiased Fisher–Yates с криптографически стойким источником случайности.
3. Для перемешанного списка `[p0, p1, ..., pn]` создаёт назначения `p[i] -> p[(i + 1) % N]`.
4. Сохраняет все назначения до раскрытия состояния и переводит игру в `ASSIGNING_WORDS`.

Для каждой попытки обязаны выполняться:

- каждый игрок является автором ровно один раз;
- каждый игрок является адресатом ровно один раз;
- автор не равен адресату;
- граф назначений является одним циклом длины `N`, а не несколькими циклами.

Пример для Маши, Пети, Вани и Саши:

```text
Маша -> Саша -> Ваня -> Петя -> Маша
```

Клиентский порядок списка участников не влияет на распределение. `Math.random()` не используется.

### 5.5 Ввод слов

- Каждый игрок получает только собственное назначение в пределах разрешённой настройкой видимости.
- Автор вводит слово или фразу длиной 1–80 символов после удаления внешних пробелов.
- Регистр и внутренние пробелы сохраняются. Одинаковые слова у разных авторов разрешены.
- До перехода к `PLAYING` автор может изменить своё слово; повторная отправка того же значения не меняет состояние.
- Игроки видят, кто уже сохранил слово, но не видят чужие слова и назначения на этом этапе.
- После сохранения последнего отсутствующего слова сервер автоматически переводит игру в `PLAYING` и фиксирует `playingStartedAt`.

### 5.6 Живая игра и подсказки

Каждый участник, включая уже угадавших, видит список всех назначений:

```text
Автор -> адресат: слово
```

Исключение — строка, где адресатом является сам пользователь:

```text
Автор -> вам: слово скрыто
```

Собственное слово не отправляется на устройство в скрытом виде. Оно отсутствует в JSON, SSE, серверном HTML и RSC-полезной нагрузке.

Все остальные слова и пары «автор — адресат» доступны всем участникам. Цепочка после распределения не управляет ходами и не требует перестройки.

### 5.7 Угадывание и результаты

- Только игрок, который ещё не угадал, может нажать «Я угадал» для себя.
- Сервер фиксирует первое успешное действие; время телефона не принимается.
- Место равно числу уже угадавших плюс один.
- Угадавший становится зрителем: остаётся в комнате и видит подсказки, но не может повторно угадать.
- При `N` участниках очки равны `N - place + 1`.
- Время результата вычисляется от `playingStartedAt` до серверного `finishedAt` результата.
- После угадывания всех участников игра автоматически переходит в `FINISHED`.

Пример для четырёх участников:

| Место | Очки |
| --- | ---: |
| 1 | 4 |
| 2 | 3 |
| 3 | 2 |
| 4 | 1 |

### 5.8 Досрочное завершение и отмена

**Досрочное завершение:**

- доступно админу только в `PLAYING` и требует подтверждения;
- сохраняет места, время и очки уже угадавших;
- создаёт для остальных результаты с `place = null`, `score = 0`;
- переводит игру в `FINISHED`;
- в финальной таблице не угадавшие идут после занявших места без номера места.

**Отмена попытки:**

- доступна админу только в `ASSIGNING_WORDS` и требует подтверждения;
- удаляет назначения, слова и результаты;
- сбрасывает готовность всех;
- очищает игровые временные метки;
- сохраняет участников, админа и настройки;
- возвращает комнату в `LOBBY`.

### 5.9 Финал

Финальный экран показывает:

- место или «Не угадал»;
- имя;
- время угадывания или прочерк;
- очки;
- полный список назначений и всех слов.

Сначала строки сортируются по `place`, затем не угадавшие — по нормализованному имени и `id`. Очки существуют только внутри текущей комнаты.

## 6. Валидация

### Имя

- удаляются внешние пробелы и повторные внутренние пробелы;
- длина после нормализации: 1–24 символа;
- уникальность внутри комнаты проверяется без учёта регистра после Unicode NFKC-нормализации;
- отображаемое имя сохраняет исходный регистр.

### Слово

- применяется только `trim`;
- длина: 1–80 символов;
- пустые и превышающие лимит значения отклоняются;
- повторы между игроками разрешены.

### Код

- ввод очищается от пробелов и приводится к верхнему регистру;
- несуществующий или неправильный код не раскрывает данные комнаты.

## 7. Пользовательский интерфейс

### Главная

Две явно разделённые операции: «Создать игру» и «Подключиться по коду». Поля имени и кода имеют подписи, ошибки рядом с полями и состояние отправки.

### Лобби

Код можно скопировать; ссылка-приглашение доступна через системное действие «Поделиться» там, где оно поддерживается. Админ видит переключатель скрытия адресата и кнопку запуска. Причина недоступности запуска отображается текстом.

### Ввод слова

Отображаются разрешённое назначение, поле, сохранённое значение и ожидание остальных. Повторная отправка не должна создавать отдельное назначение.

### Живая игра

Персональная подсказка доступна без навигации в другой раздел. Кнопка «Я угадал» требует подтверждения и блокируется во время запроса. Угадавший получает экран зрителя. Состояние SSE отображается ненавязчивым индикатором соединения.

### Финал

Рейтинг адаптируется под узкий экран: вместо горизонтальной прокрутки допускается карточное представление. Полные назначения расположены после рейтинга.

### Общие требования UX

- mobile-first, минимальная целевая ширина 360 px;
- shadcn/ui, Tailwind CSS и единые компоненты состояний;
- управление клавиатурой, видимый фокус, подписи полей и доступные диалоги;
- сенсорные цели не меньше 44×44 px;
- русский пользовательский текст и стабильные английские коды ошибок API;
- перезагрузка восстанавливает экран по серверному состоянию, а не локальному состоянию React.

## 8. Синхронизация и восстановление

- Изменения выполняются через HTTP и возвращают автору действия его актуальный персональный DTO.
- После фиксации транзакции сервер публикует SSE-событие с новой ревизией.
- Получатель события запрашивает собственный DTO; общий DTO для всех игроков не существует.
- При открытии и каждом восстановлении SSE клиент заново получает состояние.
- Пропущенное событие компенсируется сравнением ревизий и повторным запросом состояния.
- Перезагрузка или временный разрыв не удаляет игрока, назначение или результат.
- На другом устройстве автоматическое восстановление личности не поддерживается.

## 9. Нефункциональные требования

### Безопасность

- Cookie: HttpOnly, Secure в production, SameSite=Lax, ограниченный срок жизни.
- В cookie хранится только `playerId`; разрешения проверяются по БД.
- Все mutation-endpoint'ы проверяют `Origin` и принимают JSON ожидаемого типа.
- Ответы с игровым состоянием имеют `Cache-Control: no-store`.
- Создание, вход и мутации ограничиваются по частоте; превышение возвращает `429`.
- Логи содержат идентификаторы действия, комнаты, игрока и ревизии, но не слова, cookie или секреты.

### Надёжность

- Все проверки и записи одной команды выполняются атомарно.
- Команды одной комнаты сериализуются блокировкой `Game`.
- Повторное угадывание и повторная отправка неизменного слова идемпотентны.
- SSE не является источником истины; источник истины — PostgreSQL.

### Совместимость

- Актуальные стабильные мобильные Safari и Chrome.
- Постоянный self-hosted Next.js-процесс; serverless-развёртывание SSE в MVP не поддерживается.

## 10. Расширение другими играми

`Game.type` обязателен уже в MVP. В лобби доступен только `WORD_CHAIN`, поэтому отдельный переключатель игр не реализуется до появления второй игры.

Новая игра должна предоставить:

- ключ и метаданные;
- схему настроек;
- ограничения числа игроков;
- серверный модуль запуска, действий и персональной проекции;
- собственные таблицы при необходимости;
- UI-панель настроек и игровой экран;
- тесты правил и отсутствия утечек.

Core остаётся независимым от реализации игры. Смена типа игры в будущем разрешена только в `LOBBY` и должна сбрасывать игровые данные и готовность. Универсальный движок правил и динамические плагины в MVP не создаются.

## 11. Критерии приёмки

### AC-01. Создание и полный цикл из четырёх игроков

Даны четыре независимых браузерных контекста. Маша создаёт комнату, Петя, Ваня и Саша входят по коду, все готовы. После запуска каждый имеет одного адресата и одного автора, граф образует один цикл. После ввода всех слов начинается `PLAYING`. После последовательного угадывания финал содержит места 1–4 и очки 4–1.

### AC-02. Собственное слово скрыто

В `ASSIGNING_WORDS` и `PLAYING` ответ каждого игрока не содержит значение его собственного слова ни в видимых, ни в скрытых полях. Остальные слова в `PLAYING` доступны. После `FINISHED` видны все слова.

### AC-03. Скрытие адресата

При выключенной настройке автор видит имя адресата на этапе ввода. При включённой — имя и идентификатор адресата отсутствуют в его данных до `PLAYING`, после чего имя доступно в подсказке.

### AC-04. Готовность и права

Админ не может начать при менее чем трёх игроках или хотя бы одном неготовом. Обычный игрок получает отказ при изменении настроек, запуске, удалении участника и завершении.

### AC-05. Повторное и одновременное угадывание

Повторное нажатие не меняет результат. При одновременных запросах разных игроков места уникальны и соответствуют порядку принятия транзакций сервером.

### AC-06. Автоматическое и досрочное завершение

Последнее угадывание автоматически завершает игру. При досрочном завершении прошлые результаты сохраняются, оставшиеся получают ноль очков и не получают места.

### AC-07. Отмена зависшего ввода

После отмены назначения и слова удалены, готовность сброшена, участники и настройка сохранены. Админ может снова запустить игру после готовности всех.

### AC-08. Восстановление

После перезагрузки игрок остаётся тем же участником и видит актуальную фазу. После обрыва и восстановления SSE клиент получает состояние с актуальной ревизией, даже если событие было пропущено.

### AC-09. Ограничения входа

Нельзя войти после старта, создать тринадцатого игрока или использовать имя, совпадающее с существующим без учёта регистра.

### AC-10. Расширяемость

Добавление второй игры не требует изменения гостевой cookie, кода входа, готовности, формата SSE или таблицы участников. Общие модули не импортируют реализации конкретных игр.
