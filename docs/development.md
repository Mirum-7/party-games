# Разработка, запуск и проверка

Этот документ — источник истины по структуре реализации, окружению, командам и обязательным проверкам. Приложение и тестовая инфраструктура реализованы; команды ниже — фактические, а не план.

## 1. Целевая структура

```text
prisma/
├── schema.prisma
└── migrations/
src/
├── app/
│   ├── page.tsx
│   ├── game/[code]/page.tsx
│   └── api/v1/
├── components/
│   ├── ui/              # shadcn/ui
│   └── game/            # общие компоненты комнаты
├── server/              # границы описаны в architecture.md
├── shared/
│   └── contracts/       # типы API, не раскрывающие серверные секреты
└── test/
    ├── unit/
    ├── integration/
    └── e2e/
```

Игровые экраны `WORD_CHAIN` располагаются в отдельном feature-каталоге и не смешиваются с общими компонентами лобби. Prisma Client создаётся в одном server-only модуле.

## 2. Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | Да | Строка подключения PostgreSQL |
| `SESSION_PASSWORD` | Да | Секрет `iron-session`, не менее 32 символов |
| `APP_ORIGIN` | Да | Доверенный origin для проверки mutation |
| `TRUST_PROXY` | Нет | `true` — доверять `X-Forwarded-For` при определении IP для rate limiting; по умолчанию заголовок игнорируется |
| `TEST_DATABASE_URL` | Для integration-тестов | Одноразовая локальная БД, имя оканчивается на `_test` |
| `E2E_DATABASE_URL` | Для E2E-тестов | Одноразовая локальная БД, имя оканчивается на `_e2e` |
| `E2E_PORT` | Для E2E-тестов | Выделенный порт браузерного E2E; по умолчанию 3100. Внешний https-прокси слушает `https://localhost:<E2E_PORT>` (bind только на loopback), production-сервер Next стартует на заднем порту `<E2E_PORT> + 100`. Параллельные прогоны обязаны использовать `E2E_PORT`, отличающиеся минимум на 200, чтобы внешние и задние порты не пересекались (принятые выделения: 3100 по умолчанию, 3200/3400/3600 у параллельных агентов) |
| `NODE_ENV` | Управляется запуском | Режим production/development |

Локальный `APP_ORIGIN`: `http://localhost:3000`. Секреты не получают префикс `NEXT_PUBLIC_` и не коммитятся. В репозиторий добавляется только `.env.example` с безопасными fictitious-значениями.

`TRUST_PROXY` включается только при развёртывании за доверенным reverse proxy, который перезаписывает присылаемый клиентом `X-Forwarded-For` (первым адресом должен оставаться реальный IP клиента). Без этого IP для rate limiting определяется по стабильному локальному fallback, а подделанный `X-Forwarded-For` игнорируется; при `TRUST_PROXY=false` все клиенты делят один fallback-адрес, поэтому лимит действует глобально на маршрут (общая корзина) — это осознанное поведение для развёртывания без доверенного proxy.

### Одноразовая локальная PostgreSQL

Все тестовые БД — одноразовые и локальные: хост `127.0.0.1`/`localhost`, без данных разработки или production. Поднимается один контейнер на порт `127.0.0.1:55432` (образ `postgres:18`; пароль исключительно локальный):

```bash
docker run --name words-game-mvp-db -e POSTGRES_USER=words -e POSTGRES_PASSWORD=words -p 127.0.0.1:55432:5432 -d postgres:18
```

Имена БД создаются по месту: `words_game_test` (integration, `TEST_DATABASE_URL`, суффикс `_test`), `words_game_browser_e2e` (браузерный E2E, `E2E_DATABASE_URL`, суффикс `_e2e`), `words_game_migration_test` — пустая БД для проверки чистого применения миграций. Значения по умолчанию в `src/test/integration/database.ts`, `src/test/e2e/global-setup.ts` и `playwright.config.ts` уже указывают на `127.0.0.1:55432`; переопределение — только через `TEST_DATABASE_URL`/`E2E_DATABASE_URL`.

## 3. Package scripts

Фактические команды реализованного приложения:

| Команда | Назначение |
| --- | --- |
| `bun install` | Установить зависимости по lockfile |
| `bun run dev` | Запустить Next.js development server |
| `bun run build` | Выполнить `prisma generate` и production build Next.js |
| `bun run start` | Запустить постоянный production Next.js server (`next start`, порт — `--port <n>` или `PORT`) |
| `bun run lint` | Выполнить ESLint |
| `bun run typecheck` | Выполнить TypeScript без emit |
| `bun test` | Запустить unit- и integration-тесты |
| `bun run test:e2e` | Запустить Playwright E2E против тестового приложения и БД |
| `bun run db:generate` | Выполнить `prisma generate` (обязательно до migrate/build при свежем клоне) |
| `bun run db:dev` | Применить разработочные Prisma-миграции (`prisma migrate dev`) |
| `bun run db:migrate` | Применить production-миграции через `prisma migrate deploy` |

Локальный запуск (все команды выполняются через Bun; unit- и integration-тесты запускаются как `bun test` без package-скрипта):

```bash
bun install
bun run db:generate
bun run db:dev
bun run dev
```

Production:

```bash
bun install --frozen-lockfile
bun run build
bun run db:migrate
bun run start
```

Миграции запускаются отдельно и контролируемо; приложение не применяет их неявно при каждом старте реплики.

### Порядок Prisma и сохранение raw CHECK

Порядок при любом изменении схемы: сначала `bun run db:generate` (клиент обновляется от схемы), затем `bun run db:dev` для новой миграции в разработке, после правок SQL — повторный `db:generate` уже не нужен, но миграция обязана применяться к чистой БД (`words_game_migration_test`) и проходить `src/test/integration/schema.test.ts` перед коммитом.

Начальная миграция содержит шесть SQL CHECK, добавленных вручную поверх того, что генерирует Prisma, потому что схема Prisma их не выражает: `word_assignments_no_self_target`, `word_assignments_word_submission_pair`, `word_assignments_word_length`, `game_results_place_positive`, `game_results_place_time_pair`, `game_results_score_place_pair`. При будущих `prisma migrate dev` эти ограничения нельзя терять: `migrate dev` строит SQL из diff'а схемы и не знает про ручные CHECK, поэтому сгенерированную миграцию нужно проверять (и при необходимости дополнять) так, чтобы named CHECK пережили изменение, а не удалялись и не пересоздавались без нужды. Имена закреплены интеграционными тестами (constraint name + SQLSTATE), семантика — в [data-model.md](data-model.md).

## 4. Стандарты реализации

- TypeScript `strict`; `any` без обоснования запрещён.
- Игровые часы — серверные; клиентские timestamps в командах не принимаются.
- Все внешние DTO валидируются Zod. Нормализация выполняется до доменной проверки и записи.
- Чистый RNG внедряется в алгоритм распределения через зависимость, чтобы тесты были детерминированными.
- Состояние React не является источником истины после перезагрузки.
- Mutation UI показывает pending и предотвращает случайный double submit, но серверная идемпотентность обязательна независимо от UI.
- Ошибки не превращаются в успешный пустой DTO; состояния loading/error/empty различимы.
- Изменения схемы поставляются миграцией и проверкой на чистой БД.

## 5. Тестовая стратегия

Unit- и integration-тесты располагаются в `*.test.ts` и запускаются `bun test`. Playwright E2E располагается в `src/test/e2e/*.e2e.ts` и запускается только через `bun run test:e2e`; суффикс `*.e2e.ts` не даёт Bun test загрузить Playwright-файлы.

Integration- и E2E-тесты выполняются только против локальных одноразовых БД: хост `127.0.0.1` или `localhost`, имя БД оканчивается на `_test` (integration, `TEST_DATABASE_URL`) или `_e2e` (E2E, `E2E_DATABASE_URL`). Подключение тестов к development/production БД запрещено; `assertDisposableDatabaseUrl()` обрывает запуск с ошибкой `TEST_DATABASE_UNSAFE` при нарушении.

### Unit

1. Fisher–Yates и построение круга для каждого `N = 3..12`.
2. Свойства каждого назначения: нет self-loop, один вход, один выход.
3. Обход от любого игрока посещает всех ровно один раз и возвращается в начало: отдельные подциклы считаются ошибкой.
4. Готовность и допустимость запуска.
5. Формула очков, сортировка рейтинга и досрочное завершение.
6. Нормализация имён и слов.
7. Все разрешённые и запрещённые переходы.

Проверяются свойства и инварианты, а не конкретный случайный порядок.

### Integration с PostgreSQL

1. Уникальность кода, имени, автора, адресата и места — с точным именем ограничения.
2. SQL CHECK самоназначений, слов и результатов — по имени ограничения и SQLSTATE, а не «любой ошибке».
3. Каскадное удаление заполненной комнаты (players, assignments, results, настройки WORD_CHAIN).
4. Последнее слово атомарно переводит игру в `PLAYING`.
5. Одновременные `/word` не оставляют частичное состояние.
6. Одновременные `/guessed` получают уникальные последовательные места.
7. Повтор `/guessed`, включая повтор последнего угадывания после `FINISHED`, не меняет результат и ревизию и возвращает 200.
8. Гонка `/guessed` и `/finish` имеет детерминированный результат по порядку commit.
9. `/cancel` удаляет назначения и результаты, сбрасывает готовность, сохраняет настройки.
10. Выход админа передаёт роль; отключение SSE — нет.
11. Каждая mutation после commit публикует ровно ту ревизию, которая сохранена; идемпотентный no-op не публикует изменение.

Интеграционные тесты используют отдельную тестовую PostgreSQL и не запускаются против development/production БД.

### Тесты персональных проекций

Для каждой фазы и каждого игрока проверять сериализованный ответ, а не только отображение:

- собственное слово отсутствует до финала;
- при включённом скрытии `target.id` и имя адресата отсутствуют в `setup` до `PLAYING`;
- чужие слова отсутствуют в `ASSIGNING_WORDS`;
- в `PLAYING` скрыто ровно одно значение — собственное слово вызывающего;
- в `FINISHED` все слова раскрыты;
- SSE не содержит игровые данные;
- RSC/HTML не содержит значений, отсутствующих в разрешённом DTO.

Для проверки утечек недостаточно искать поле `word`: нужно сравнивать сериализованный ответ с фактическими секретными значениями, чтобы обнаружить их в неожиданном поле.

### E2E

#### Транспорт браузерного E2E: production Next за тест-only TLS-прокси

Браузерный трафик E2E идёт через `https://localhost:<E2E_PORT>`, а не напрямую по http. Причина: сессионная cookie в production-режиме `Secure` (`buildSessionOptions(password, NODE_ENV === "production")`), а WebKit не отправляет `Secure`-cookie по http даже на `localhost`/`127.0.0.1` (Chromium делает локальное исключение, WebKit — нет): cookie сохраняется, но не передаётся, и каждый браузерный сценарий падает на первом шаге. Реальный TLS полностью сохраняет семантику `Secure`-cookie и production-сервер Next.

Организация (всё — только тестовое окружение, зависимостей не добавлено):

- `src/test/e2e/tls-proxy.ts` — TLS-терминатор на `node:https`/`node:http` без буферизации, включая долгоживущий SSE-поток. Запускается как `webServer` Playwright: сам стартует `bun run start --port <E2E_PORT + 100>` (plain http на `127.0.0.1`), дожидается его (с drain ответов опроса), слушает `https://localhost:<E2E_PORT>` и привязан только к loopback `127.0.0.1`. Обрыв клиентского запроса или ответа обязательно распространяется на backend (`proxy.destroy()`/`upstream.destroy()`), чтобы abort доходил до сервера, а закрытые браузером SSE-потоки освобождались сразу.
- Сертификат самоподписанный (`CN=localhost`, SAN `localhost`/`127.0.0.1`), генерируется локально через `openssl` и кэшируется в `node_modules/.cache/words-game-e2e-tls/` (в git не попадает). Публикация атомарна и самовосстанавливающаяся: ключ и сертификат объединяются в один PEM и выкладываются одним `rename` из временного каталога процесса, повреждённый кэш перегенерируется, временные каталоги удаляются (helper `src/test/e2e/tls-cert.ts`, unit-тесты `src/test/unit/e2e-tls-cert.test.ts`). Требуется доступный `openssl`.
- Браузерные контексты и readiness-проверка `webServer` доверяют ему через `ignoreHTTPSErrors` только в `playwright.config.ts`; тестовый секрет, загаданные слова и поведение cookie не меняются.
- `APP_ORIGIN` production-сервера в E2E — видимый браузеру origin `https://localhost:<E2E_PORT>` (проверка `Origin` мутаций сравнивает с ним). Единый источник origin — константа `APP_ORIGIN` в `src/test/e2e/helpers.ts`; конфигурация Playwright и SSE-тесты импортируют её, рассинхрон невозможен (регрессия: `src/test/unit/e2e-origin.test.ts`).
- «Голые» HTTP-запросы из процесса тестов (живой SSE-поток в `sse.e2e.ts`) используют `e2eFetch`/`e2eFetchStream` из helpers: `node:https` с явным `rejectUnauthorized: false` только для этого прокси (`NODE_EXTRA_CA_CERTS` не подходит — рантайм читает его один раз при старте).

#### Сценарии

Обязательный сценарий использует четыре Playwright browser context, а не четыре вкладки с общей cookie:

1. Маша создаёт комнату.
2. Петя, Ваня и Саша входят по коду.
3. Все отмечают готовность; админ запускает.
4. Каждый вводит слово; проверяется корректная персональная подсказка.
5. Игроки угадывают в известном порядке.
6. Финал показывает места 1–4 и очки 4–1.

Дополнительные E2E:

- скрытие адресата включено до старта;
- досрочное завершение с не угадавшими;
- отмена ввода и повторный запуск;
- перезагрузка в каждой фазе;
- разрыв и восстановление SSE с пропущенным событием;
- попытка действия обычным игроком от имени админа;
- мобильный viewport 360 px и работа с открытой клавиатурой.

## 6. Обязательная проверка перед завершением изменения

Минимальный набор для кода:

```bash
bun run lint
bun run typecheck
bun test
bun run build
```

Если изменены пользовательские сценарии, API, проекции или синхронизация, дополнительно обязателен соответствующий `bun run test:e2e`. При изменении схемы миграции дополнительно применяются к чистой тестовой БД.

Нельзя объявлять изменение завершённым, если обязательные проверки не запускались или завершились ошибкой. Нельзя считать unit-тесты доказательством отсутствия утечки в реальном HTTP/RSC-ответе.

## 7. Проверка документации

При изменении только документации:

- проверить относительные ссылки;
- проверить отсутствие `TODO`, `TBD` и незаполненных заглушек;
- сверить статусы, лимиты, формулу очков и настройки во всех затронутых документах;
- обновить источник истины, но не дублировать подробности без необходимости;
- не добавлять рабочие заметки и историю в `AGENTS.md`.
