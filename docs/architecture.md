# Архитектура

Этот документ — источник истины по модульным границам, гостевым сессиям, SSE и развёртыванию. Продуктовые правила находятся в [спецификации](superpowers/specs/2026-11-22-words-game-design.md).

## 1. Решение

MVP реализуется как **модульный монолит Next.js**:

```text
Мобильный браузер
  ├── HTTPS: страницы, команды, персональное состояние
  └── SSE: уведомления о новых ревизиях
             │
             ▼
Постоянный Next.js-процесс
  ├── Core: комнаты, игроки, cookie, ревизии, SSE
  ├── Реестр игр
  └── Модуль WORD_CHAIN
             │
             ▼
         PostgreSQL
```

Отдельный backend не создаётся. Он добавляет второй деплой, CORS и распределённую обработку cookie, но не даёт преимуществ для одной игры на 3–12 участников. Серверный код изолирован так, чтобы его можно было вынести позже без переноса продуктовых правил в UI.

## 2. Технологический контур

- **Next.js App Router, React, TypeScript:** страницы и Route Handlers.
- **PostgreSQL:** постоянный источник истины.
- **Prisma:** типизированный доступ и миграции; критические SQL-ограничения допускаются в миграциях.
- **Bun:** единственный рантайм приложения — установка зависимостей, package scripts, production-сервер (`bun run start`) и unit/integration-тесты.
- **Next.js production server:** один долгоживущий self-hosted процесс, запускаемый через Bun; runtime и версии фиксируются lockfile.
- **shadcn/ui + Tailwind CSS:** mobile-first UI.
- **Zod:** серверная валидация входных DTO и настроек.
- **iron-session:** зашифрованная гостевая cookie.
- **SSE через Route Handler:** однонаправленные уведомления сервера.

Prisma 7 с driver adapter `@prisma/adapter-pg` официально поддерживает Bun runtime. Отдельные CLI-подкоманды Prisma могут под капотом использовать Node — это деталь реализации инструмента, приложение и тесты всегда идут на Bun.

## 3. Модули и зависимости

Целевая структура серверного кода:

```text
src/server/
├── core/
│   ├── auth/           # cookie, playerId, проверка участника
│   ├── games/          # создание, код, общие состояния Game
│   ├── players/        # вход, готовность, выход, админ
│   ├── results/        # общая запись результатов
│   └── realtime/       # интерфейс publisher/subscriber, SSE
├── games/
│   ├── registry.ts     # composition root реестра
│   └── word-chain/
│       ├── rules.ts        # чистые правила и построение цикла
│       ├── service.ts      # транзакционные команды
│       ├── projection.ts   # персональный DTO
│       ├── schemas.ts      # Zod-схемы
│       └── types.ts
├── db.ts
└── http/               # аутентификация запроса и единый формат ошибок
```

Правила зависимостей:

1. Core определяет общие типы и не импортирует `server/games/*`.
2. Игровой модуль может использовать публичные сервисы Core.
3. `games/registry.ts` является composition root и связывает тип игры с модулем.
4. Route Handlers валидируют HTTP-вход, вызывают сервис и возвращают результат; игровых правил в маршрутах нет.
5. UI зависит от контрактов, а не от Prisma-моделей.
6. Prisma Client и серверные сервисы не импортируются в Client Components.
7. Чистые правила не зависят от Next.js, HTTP и Prisma и тестируются отдельно.

Не создаются динамические плагины, универсальный язык игровых действий или общая JSON-модель всех будущих игр.

## 4. Гостевая сессия

Используется `iron-session`, поддерживающий Next.js App Router и перечисленный в [официальном руководстве Next.js по аутентификации](https://nextjs.org/docs/app/guides/authentication). Поведение и параметры библиотеки фиксируются по [документации `iron-session`](https://github.com/vvo/iron-session).

Cookie содержит только:

```ts
type GuestSession = {
  playerId: string;
};
```

Требования:

- `cookieName = "wg_session"`;
- `httpOnly = true`, `sameSite = "lax"`, `path = "/"`;
- `secure = true` в production;
- срок жизни — 7 дней, без бессрочных cookie;
- секрет берётся из `SESSION_PASSWORD` и не попадает в клиентский bundle;
- в cookie нет имени, кода, роли админа, готовности, слов или настроек.

При каждом защищённом запросе сервер расшифровывает cookie, загружает `Player` и проверяет соответствие `gameId` из URL. Права админа определяются текущим `Game.hostPlayerId`, а не cookie. Несуществующий игрок или игрок другой комнаты не получает доступ.

`Auth.js` не используется: регистрация, аккаунты, OAuth и постоянная личность между устройствами не входят в MVP.

При входе в другую комнату cookie заменяется после успешной транзакции. При выходе cookie удаляется. Потеря cookie означает потерю автоматического восстановления личности; вход по имени и коду не даёт право занять существующего игрока.

## 5. HTTP и персональная проекция

Route Handlers образуют версионированный API `/api/v1`. Каждая команда:

1. Проверяет `Origin`, Content-Type и входную Zod-схему.
2. Для защищённой команды аутентифицирует `playerId` и авторизует действие; создание и новый вход используют публичный сценарий.
3. Выполняет транзакционный сервисный метод.
4. Возвращает вызывающему его актуальную проекцию состояния.
5. После фактического изменения и commit публикует ревизию через realtime-интерфейс.

Персональная проекция строится отдельно для каждого `viewer`. Нельзя получить полный набор слов и затем удалять поля в React. Нельзя использовать один общий кешируемый DTO для всех участников.

Server Components используют ту же проекцию через прямой вызов сервиса, а не внутренний HTTP-запрос. Ограничения распространяются и на RSC-полезную нагрузку.

## 6. SSE

### Назначение

SSE сообщает, что состояние изменилось. Он не переносит игровые слова, назначения, состав DTO или результаты.

### Publisher

Core определяет интерфейс:

```ts
interface GameRealtime {
  publish(gameId: string, revision: number): void;
  subscribe(gameId: string, listener: (revision: number) => void): () => void;
}
```

MVP использует in-memory реализацию внутри одного Next.js-процесса. Игровые сервисы зависят от интерфейса, а не от Map или конкретного Route Handler.

### Последовательность

1. Клиент открывает `/api/v1/games/{code}/events`.
2. Сервер проверяет cookie и членство до открытия потока.
3. Клиент при `open` запрашивает своё состояние.
4. Сервер отправляет текущую ревизию после установки подписки.
5. При `game.changed` с ревизией выше локальной клиент запрашивает состояние.
6. Браузер переподключает `EventSource`; на каждом `open` выполняется полная синхронизация.
7. Комментарий `: ping` каждые 15 секунд предотвращает закрытие простаивающего соединения прокси.

Заголовки ответа:

```text
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

События не сохраняются в БД. `Game.revision` и запрос снимка устраняют необходимость durable event log для MVP.

### Ограничение экземпляров

In-memory publisher работает только при одном приложении-процессе. Запуск нескольких replicas без общего Pub/Sub запрещён, потому что событие может быть опубликовано не в том процессе, где находится SSE-клиент.

При необходимости масштабирования реализация `GameRealtime` заменяется на Redis Pub/Sub либо realtime выделяется в backend. Контракт HTTP/SSE и игровые модули при этом не меняются.

Требования self-hosting и потоковой передачи соответствуют [официальному руководству Next.js](https://nextjs.org/docs/app/guides/self-hosting): прокси и load balancer должны пропускать streaming без буферизации.

## 7. Транзакции и согласованность

- Все команды активной комнаты блокируют её строку `Game` через `SELECT ... FOR UPDATE` внутри транзакции.
- Проверка состояния выполняется после получения блокировки.
- Запись действия, изменение фазы/результата и увеличение `revision` происходят в одной транзакции.
- Публикация SSE выполняется только после успешного commit.
- Неизменившая состояние идемпотентная операция не увеличивает ревизию.
- Порядок блокировки транзакций определяет порядок одновременных результатов.

Подробные последовательности находятся в [модели данных](data-model.md).

## 8. Наблюдаемость и ошибки

Структурный лог mutation содержит `action`, `gameId`, `playerId`, результат и новую `revision`. Не логируются request body целиком, слова, cookie, `SESSION_PASSWORD` и `DATABASE_URL`.

Ошибки классифицируются как валидация, отсутствие аутентификации, запрет доступа, отсутствие ресурса, конфликт состояния и превышение лимита. Внутренние ошибки возвращают общий код и correlation ID; stack trace клиенту не отправляется.

## 9. Развёртывание

MVP состоит из:

- одного постоянного Next.js-процесса;
- одной PostgreSQL;
- reverse proxy с HTTPS и отключённой буферизацией SSE;
- резервного копирования БД на уровне инфраструктуры.

Serverless-функции и несколько replicas без общего realtime-канала не поддерживаются. Graceful shutdown прекращает приём новых соединений и завершает активные mutation перед остановкой.

## 10. Путь к отдельному backend

Выделение оправдано только при появлении подтверждённых требований: несколько realtime-узлов, сложные таймеры, несколько игр с разными жизненными циклами или самостоятельное масштабирование.

Подготовка уже обеспечивается версионированным API, отсутствием правил в UI, чистыми игровыми модулями и интерфейсом `GameRealtime`. Перенос не должен сопровождаться переписыванием правил `WORD_CHAIN`.
