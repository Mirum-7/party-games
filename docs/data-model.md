# Модель данных и транзакции

Этот документ — источник истины по сущностям, ограничениям и транзакционным последовательностям. Правила использования данных описаны в [спецификации](superpowers/specs/2026-11-22-words-game-design.md).

## 1. Хранилище

Используется PostgreSQL. Идентификаторы сущностей — UUID в формате `String` Prisma. Все временные метки хранятся как `DateTime` в UTC. Точные аннотации Prisma могут уточняться без изменения описанных инвариантов.

Физически nullable-поля, необходимые для разрешения циклических связей, не ослабляют сервисные инварианты.

## 2. Общие enum

```text
GameType:
  WORD_CHAIN

GameStatus:
  LOBBY
  ACTIVE
  FINISHED

WordChainPhase:
  ASSIGNING_WORDS
  PLAYING
```

Публичная фаза вычисляется так:

| Game.status | WordChainGame.phase | Публичная фаза |
| --- | --- | --- |
| LOBBY | null | LOBBY |
| ACTIVE | ASSIGNING_WORDS | ASSIGNING_WORDS |
| ACTIVE | PLAYING | PLAYING |
| FINISHED | PLAYING | FINISHED |

Другие сочетания недопустимы.

## 3. Сущности

### Game

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| id | UUID, PK | Внутренний идентификатор |
| code | String(6), unique | Публичный код комнаты |
| type | GameType | Тип игры, в MVP `WORD_CHAIN` |
| status | GameStatus | Общий статус комнаты |
| hostPlayerId | UUID?, unique, FK Player | Текущий админ |
| revision | Int, default 0, >= 0 | Версия состояния |
| createdAt | DateTime | Создание |
| updatedAt | DateTime | Последнее изменение записи |
| startedAt | DateTime? | Запуск текущей попытки |
| finishedAt | DateTime? | Завершение |

Сервисный инвариант: любая непустая комната имеет ровно одного админа среди своих игроков. `hostPlayerId` nullable только для допустимого создания/удаления связей.

`revision` увеличивается на единицу при каждом фактическом изменении доступного клиентам состояния. Он не уменьшается при отмене.

### Player

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| id | UUID, PK | Идентификатор участника |
| gameId | UUID, FK Game | Комната |
| name | String(24) | Отображаемое имя |
| normalizedName | String | Ключ уникальности имени |
| isReady | Boolean, default false | Готовность в лобби |
| joinedAt | DateTime | Вход в комнату |

Ограничения и инварианты:

- `UNIQUE(gameId, normalizedName)`;
- игрок принадлежит только одной комнате;
- разрыв сети не изменяет запись;
- онлайн-статус по SSE не сохраняется и не влияет на правила;
- удаление возможно только в `LOBBY`.

### GameResult

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| id | UUID, PK | Идентификатор результата |
| gameId | UUID, FK Game | Комната |
| playerId | UUID, FK Player | Игрок |
| place | Int? | Место; null для не угадавшего |
| score | Int, default 0, >= 0 | Очки внутри игры |
| finishedAt | DateTime? | Серверное время угадывания |

Ограничения:

- `UNIQUE(gameId, playerId)`;
- `UNIQUE(gameId, place)`; PostgreSQL допускает несколько null;
- `place >= 1`, если задано;
- `finishedAt IS NOT NULL` iff `place IS NOT NULL`;
- `score > 0` iff `place IS NOT NULL`.

Последние три правила закрепляются именованными SQL CHECK в миграции: `game_results_place_positive`, `game_results_place_time_pair`, `game_results_score_place_pair`. Имена и SQLSTATE зафиксированы `src/test/integration/schema.test.ts`, при будущих `migrate dev` ограничения сохраняются (порядок — в [development.md](development.md)). Для будущих игр с другой семантикой результатов допускается отдельная модульная таблица вместо изменения смысла существующих полей. Длина значения дополнительно ограничена типом колонки.

### WordChainGame

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| gameId | UUID, PK, FK Game | Связь один-к-одному |
| phase | WordChainPhase? | Фаза активной попытки |
| hideTargetNamesDuringSetup | Boolean, default false | Настройка лобби |
| playingStartedAt | DateTime? | Начало этапа угадывания |

Запись создаётся вместе с `Game`, чтобы настройки были доступны уже в лобби. В `LOBBY` `phase` и `playingStartedAt` равны null. В `FINISHED` сохраняется `PLAYING` и время начала для расчёта результатов.

### WordAssignment

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| id | UUID, PK | Идентификатор назначения |
| gameId | UUID, FK Game | Комната |
| authorPlayerId | UUID, FK Player | Кто загадывает |
| targetPlayerId | UUID, FK Player | Кому загадывают |
| word | String(80)? | Значение до/после ввода |
| submittedAt | DateTime? | Последнее сохранение слова |
| createdAt | DateTime | Создание назначения |

Ограничения:

- `UNIQUE(gameId, authorPlayerId)` и глобальный `@unique` по `authorPlayerId`;
- `UNIQUE(gameId, targetPlayerId)` и глобальный `@unique` по `targetPlayerId`;
- SQL CHECK `word_assignments_no_self_target`: `authorPlayerId <> targetPlayerId`;
- `word_assignments_word_submission_pair`: `word IS NOT NULL` iff `submittedAt IS NOT NULL`;
- `word_assignments_word_length`: `word` после `trim` непустое и не длиннее 80 символов; тип колонки `VARCHAR(80)` отсекает более длинные значения раньше CHECK.

Сервис дополнительно гарантирует, что автор и адресат принадлежат `gameId`. Уникальности по отдельности не доказывают наличие одного цикла: это проверяет алгоритм и property-тесты.

Связи с `Game` и `Player` используют каскадное удаление только там, где оно соответствует удалению всей комнаты. Перед удалением отдельного игрока в лобби сервис проверяет отсутствие активных назначений и результатов.

## 4. Связи

```text
Game 1 ─── * Player
Game 1 ─── * GameResult
Game 1 ─── 0..1 WordChainGame
Game 1 ─── * WordAssignment
Player 1 ─── 0..1 GameResult
Player 1 ─── 0..1 WordAssignment как автор в рамках игры
Player 1 ─── 0..1 WordAssignment как адресат в рамках игры
Player 1 ─── 0..1 Game как админ
```

Отдельной таблицы `Session` нет: `iron-session` хранит подписанные и зашифрованные данные в cookie. Каждая авторизация всё равно обращается к `Player` и `Game`.

## 5. Транзакционный протокол

### Общий протокол команды существующей комнаты

1. Начать транзакцию.
2. Выполнить `SELECT ... FOR UPDATE` для строки `Game`.
3. Проверить существование игрока, членство, права и фазу после блокировки.
4. Выполнить команду и связанные ограничения.
5. При фактическом изменении увеличить `Game.revision`.
6. Commit.
7. Построить ответ вызывающему и опубликовать SSE с новой ревизией.

Ответ не должен читать незафиксированные данные. Публикация до commit запрещена.

### Создание комнаты

1. Нормализовать имя и тип игры.
2. Сгенерировать код криптографически стойким RNG; при unique collision повторить.
3. Создать `Game`, игрока-админа и `WordChainGame` с настройками по умолчанию.
4. Установить `hostPlayerId` и вернуть персональный DTO.
5. Установить cookie только после успешного commit.

### Вход

1. Найти комнату по нормализованному коду.
2. Если cookie уже ссылается на игрока этой комнаты, вернуть его состояние без дубликата.
3. Проверить `LOBBY`, лимит 12 и уникальность имени.
4. Создать игрока, увеличить ревизию, commit.
5. Установить cookie и вернуть DTO нового игрока.

Unique collision имени или кода преобразуется в доменный конфликт, а не внутреннюю ошибку.

### Запуск `WORD_CHAIN`

1. Проверить админа, `LOBBY`, `3 <= N <= 12` и готовность всех.
2. Заблокировать или зафиксировать детерминированный исходный список игроков внутри транзакции.
3. Перемешать unbiased Fisher–Yates и создать единый цикл.
4. Проверить инварианты графа до записи.
5. Установить `Game.status = ACTIVE`, `startedAt = now`, `WordChainGame.phase = ASSIGNING_WORDS`.
6. Увеличить ревизию и зафиксировать всё одним commit.

Если любая запись назначения нарушает ограничение, вся попытка откатывается.

### Сохранение слова

1. Проверить автора и `ASSIGNING_WORDS`.
2. Найти назначение по `(gameId, authorPlayerId)`.
3. Если нормализованное слово совпадает с сохранённым, вернуть состояние без ревизии.
4. Обновить `word` и `submittedAt`.
5. Если все назначения комнаты содержат слова, установить `phase = PLAYING`, `playingStartedAt = now`.
6. Увеличить ревизию один раз и commit.

Редактирование после `PLAYING` отклоняется.

### Угадывание

1. Проверить игрока.
2. Если `GameResult` с местом уже существует, вернуть текущее состояние без изменения места, времени, очков и ревизии, в том числе если игра уже завершена последним угадыванием.
3. Проверить `PLAYING`; если результата нет и фаза другая, вернуть конфликт состояния.
4. `place = count(existing results with place not null) + 1`.
5. `score = N - place + 1`, `finishedAt = now`.
6. Создать результат.
7. Если `place = N`, установить `Game.status = FINISHED` и `Game.finishedAt = now`.
8. Увеличить ревизию и commit.

Блокировка `Game` сериализует одновременные запросы и исключает одинаковые места.

### Досрочное завершение

1. Проверить админа и `PLAYING`.
2. Для каждого игрока без результата создать `{ place: null, score: 0, finishedAt: null }`.
3. Сохранить существующие результаты без изменений.
4. Установить `FINISHED` и `finishedAt = now`.
5. Увеличить ревизию и commit.

Гонка с угадыванием разрешается порядком блокировки: если угадывание зафиксировано первым, оно входит в результат; если завершение первым, последующее угадывание отклоняется как недопустимое в `FINISHED`.

### Отмена ввода слов

1. Проверить админа и `ASSIGNING_WORDS`.
2. Удалить все `WordAssignment` и `GameResult` попытки.
3. Установить всем `Player.isReady = false`.
4. Установить `Game.status = LOBBY`, `startedAt = null`, `finishedAt = null`.
5. Установить `WordChainGame.phase = null`, `playingStartedAt = null`.
6. Сохранить игроков, админа и настройку; увеличить ревизию и commit.

### Выход и удаление в лобби

- Операции разрешены только в `LOBBY`.
- Удаление чужого игрока требует прав админа; админ не удаляет себя через этот endpoint.
- При самостоятельном выходе админа роль передаётся до удаления по `(joinedAt, id)`.
- Удаление последнего игрока удаляет комнату и связанные записи.
- Ревизия увеличивается, если комната остаётся.

## 6. Персональное чтение

Чтение состояния не блокирует комнату. Оно получает согласованный набор записей и строит DTO для конкретного `viewer`:

- в лобби нет назначений;
- на вводе слов автор получает только своё назначение и только разрешённый набор полей;
- в живой игре значение `word` исключается, если `targetPlayerId = viewer.playerId`;
- на финале все слова доступны.

Запрещено сначала сериализовать полный DTO и затем маскировать значения на клиенте.

## 7. Очистка и хранение

В MVP результаты доступны, пока существует комната и действительна cookie. Автоматическая retention-политика не реализуется. Перед появлением постоянного рейтинга или истории потребуется отдельная модель личности; записи гостевых `Player` не должны неявно превращаться в аккаунты.
