## Неснимаемые игровые инварианты

1. Игра `WORD_CHAIN` допускает от 3 до 12 участников.
2. При запуске все участники образуют ровно один направленный цикл. Самоназначения, повторные адресаты, повторные авторы и отдельные подциклы запрещены.
3. Цепочка нужна только для первоначального распределения. После ввода слов результат каждого игрока независим.
4. Игрок не должен получать загаданное ему слово до финала: ни в JSON, ни в SSE, ни в HTML/RSC-полезной нагрузке, ни в логах.
5. При включённой настройке `hideTargetNamesDuringSetup` идентификатор и имя адресата не отправляются автору до перехода к `PLAYING`.
6. Скрытие интерфейсом или CSS не считается защитой. Нужна персональная серверная проекция данных.
7. Первое принятое сервером событие угадывания фиксирует время, место и очки. Повторные запросы не изменяют результат.
8. Очки рассчитываются как `N - place + 1`; не угадавшие при досрочном завершении получают 0 очков и не получают место.

## Архитектурные границы

- Core отвечает за комнаты, участников, готовность, админа, гостевые сессии, ревизии и SSE.
- Игровой модуль отвечает за свои настройки, правила, действия, проекции и результаты.
- Core не импортирует реализации конкретных игр. Связывание выполняется только через реестр в composition root.
- Не создавать универсальный движок игр, динамическую загрузку плагинов или отдельный backend без новой подтверждённой потребности.
- Все команды изменяют состояние только на сервере. Проверка прав на клиенте не заменяет серверную авторизацию.
- Каждая команда одной комнаты выполняется в транзакции с блокировкой строки `Game`, изменяет состояние и `revision` атомарно.
- SSE переносит только метаданные синхронизации. Слова и персональные DTO передаются только через авторизованный запрос состояния.

## Безопасность и данные

- В cookie хранится только `playerId`; админство, готовность и игровые данные каждый раз проверяются по БД.
- Использовать HttpOnly, Secure в production, SameSite=Lax и серверный секрет сессии из окружения.
- Все входные данные валидируются на сервере. Ответы состояния имеют `Cache-Control: no-store`.
- Секреты, cookie и загаданные слова не записываются в журналы.
- Изменения схемы выполняются через Prisma-миграции. Критические игровые ограничения дополнительно проверяются тестами.

## Проверка изменений

- Для изменения правил обязательны тесты переходов, разрешений и персональных проекций.
- Для алгоритма распределения проверять все размеры от 3 до 12 и свойство одного цикла, а не только уникальность назначений.
- Для действий с записью проверять повторные и одновременные запросы.
- Для пользовательского сценария обязателен E2E с четырьмя независимыми браузерными контекстами.
- Перед завершением выполнять проверки из `docs/development.md`; нельзя сообщать о готовности при failing checks.
